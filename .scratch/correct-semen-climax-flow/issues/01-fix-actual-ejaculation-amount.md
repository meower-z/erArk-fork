# 01 — 修正临时精液参与时的实际射精量

**What to build:** 当一次射精同时消耗临时精液和基础精液时，所有下游系统都收到屏幕所显示的完整实际射精量。临时精液只决定从哪一类资源中扣除，不再缩小返回给污浊、射精位置、受孕刷新、料理等调用方的数量。

**Blocked by:** None — can start immediately

**Status:** ready-for-agent

- [ ] 无临时精液时，显示量、返回量、基础精液减少量和全局精液总量增量保持既有一致关系。
- [ ] 临时精液大于 0 且小于实际射精量时，返回量仍等于完整实际射精量，而临时精液先被正确消耗、剩余部分由基础精液承担。
- [ ] 临时精液恰好等于实际射精量时，返回值保持为正的完整实际射精量，下游不再进入“没有射精”的分支。
- [ ] 临时精液大于实际射精量时，只消耗所需的临时精液，基础精液不减少，返回量仍等于完整实际射精量。
- [ ] 每个边界用例中，屏幕显示量、函数返回量、基础与临时精液合计减少量以及全局精液总量增量描述同一次实际射精。
- [ ] 自动回归测试复用既有 near-real 无 GUI 引导，在通用射精行为边界覆盖上述四个精液来源分区，不依赖局部变量名或内部扣除步骤。
- [ ] 若现有 near-real 测试无需新增生产接缝即可到达料理流程，补充“临时精液恰好供给完整射精时料理不误报材料不足”的行为验证；否则以通用射精回归测试为必需自动证据，并在 Tk 验证中覆盖一个清楚的下游玩家可见结果。
- [ ] 使用同一存档、设置、随机结果和操作捕获独立的 Tk 修复前后证据，截图能看清实际射精量及其下游成功或记录差异。
- [ ] 改动只修正实际射精量返回契约，不引入无精液高潮语义、衣柜菜单守卫或其他射精流程清理。
- [ ] 数据构建或生成文件仅在仓库正常流程确实要求时更新；最终 diff 通过项目标准和本票行为范围两轴审查。
