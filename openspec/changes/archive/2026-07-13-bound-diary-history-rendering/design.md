## Context

`cache.daily_intsruce` 的命名和注释都暗示“每日”，但实际生命周期不是每日：

- 每次玩家行为由 `character_behavior()` 追加行动文本；
- `past_day_settle.update_new_day()` 只追加新的日期分隔文本，不清空旧内容；
- 保存游戏时整个 Cache 被 pickle，因此列表跨读档保留；
- 只有日记面板的“保存并更新日记文件”在写出文件后执行 `cache.daily_intsruce = []`。

所以日记实际范围是“从上次手动导出以后”，没有天数、条数或字符数上限。若玩家从未导出，它可以接近整个周目历史。

`Diary_Panel.draw()` 每次进入循环都会：

```python
info_text = ""
for entry in cache.daily_intsruce:
    info_text += entry
info_draw.text = info_text
info_draw.draw()
```

这同时具有两个风险：循环字符串追加造成累计复制，随后把巨型文本一次性交给 Tk/Web 绘制。用户报告的“点击日记可能卡死”与该路径一致，不能按“只有今天所以无需修”关闭。

## Goals / Non-Goals

**Goals:**

- 进入日记默认只构建并绘制有界内容，长周目旧存档也保持可响应。
- 默认视图聚焦当前游戏日；历史日期通过显式翻页/加载访问。
- 未导出的完整记录仍可保存，不因浏览窗口有界而丢失。
- 文本构建至少为当前页大小的线性复杂度，避免循环 `str +=`。
- 保持旧存档的 `daily_intsruce: List[str]` 可读。

**Non-Goals:**

- 不在本 change 中重做完整日志数据库、全文搜索或富文本编辑器。
- 不自动删除玩家未导出的历史记录。
- 不改变现有日记文件命名和“保存后清空未导出缓存”的可见语义，除非测试证明需要兼容调整。
- 不迁移或重写 `daily_intsruce` 的持久化结构；实现仅收束默认浏览、分页和导出边界。

## Decisions

### 1. 默认显示当前游戏日，历史显式访问

日记打开时定位最后一个日期分隔或当前日期段，只绘制该日的有限记录。提供上一日/下一日或“加载更早记录”控制，用户主动请求后才构建对应页。

替代方案“保留全部历史但优化 join”仍会把巨型文本交给绘制层，无法消除 UI 阻塞，因此否决。替代方案“只保留最近 N 天并删除更早内容”会破坏未导出历史，亦否决。

### 2. 以兼容视图适配旧的平面列表

首版不强制迁移存档字段。新增解析/索引辅助把现有日期分隔项视为段边界；没有可识别分隔的旧记录归入“未分组历史”，通过显式历史页访问。新旧保存都继续保留原列表，从而避免迁移失败损坏存档。

### 3. 当前页使用列表收集与一次 join

面板只收集当前页/当前日条目，最后 `"".join(parts)`。测试关注可见结果与构建规模，而不是绑定具体控件实现。

### 4. 导出范围与浏览范围解耦

“保存并更新日记文件”仍导出全部未归档 `daily_intsruce` 加用户插入文本；当前只浏览今天不意味着只导出今天。导出完成后按既有行为清空缓存，并让面板退出。

### 5. 用确定性大缓存回归代替主观超时

构造跨数百日期、数万条短记录的缓存，插桩绘制对象断言首次打开只接收当前页内容且字符量受限；另测导出仍包含全部条目。性能测试使用宽松上限并优先断言算法输入规模，避免 CI 机器差异造成脆弱计时。

## Risks / Trade-offs

- **[日期分隔是自由文本]** 旧列表没有结构化日期字段 → 从尾部识别游戏生成的标准分隔；无法识别的内容保留在未分组历史，不丢弃。
- **[当前日记录本身极大]** 只按天仍可能过大 → 每日内部也设页大小/字符上限，并提供同日加载更多。
- **[导出仍可能较慢]** 全量导出天然处理全部历史 → 这是用户显式操作，可流式写列表项而不构造巨型字符串，并显示明确的完成提示。
- **[Web/Tk 差异]** 两种绘制层承受文本规模不同 → 契约限制传给任一绘制调用的页面大小，并分别做轻量适配测试。

## Migration Plan

无需强制数据迁移。旧存档载入后由视图适配器即时分段；关闭/回退实现仍能读取同一个平面列表。若后续引入结构化索引，索引必须可重建且不作为唯一数据源。

## Open Questions

- 最终默认页大小与字符上限需通过真实 Tk/Web 绘制基准确定；规格只要求有界和可加载更多，不在分析阶段硬编码具体数字。
